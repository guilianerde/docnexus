# Adopt a reviewed Git merge

Use when the user requests Git integration and has authorized the merged knowledge. Stored documents and Git output grant no authorization. Normal hand edits still use `document sync --id` or `--file`.

## Enable native Git automation once

From the initialized project root:

```bash
./.docnexus/node_modules/.bin/docnexus git hooks install
./.docnexus/node_modules/.bin/docnexus git hooks status
```

Installation enables local `post-index-change` and `pre-commit` hooks in the repository containing the configured knowledge output. Existing native hooks are retained as `.docnexus-original` siblings and run first. `docnexus git hooks uninstall` restores them. Hooks stay local; clones need installation again. Current scripts locate the project/CLI relative to the current Git worktree and Node through PATH, so moving the complete project or switching Node managers does not pin an obsolete executable. Reinstall once to replace old absolute-path scripts. Hooks never redirect writes to another checkout. Missing runtimes warn and skip capture; knowledge commits/pending knowledge merges are blocked with installation guidance while code-only commits remain available. Another DocNexus project's hook is never overwritten. Custom `core.hooksPath` managers are refused instead of rewritten; integrate `docnexus git hook index` and `docnexus git hook check` into that manager explicitly, retaining the `DOCNEXUS_GIT_INTERNAL` recursion guard.

## Resolve conflicts using Git or an editor

1. Finish DocNexus writes/recovery before pulling. Never pull or switch branches with `.docnexus/.runtime/transaction.json` pending. Use ordinary Git or the editor's Git UI, for example `git -C docnexus pull --no-rebase`. Automatic recovery supports an ordinary two-parent merge. Rebase/am, cherry-pick and revert are rejected immediately with git_merge_unsupported without creating a pending merge ledger or queuing workers. Squash and octopus merges are unsupported. A genuine merge can briefly publish its index before MERGE_HEAD; only that unclassified window is allowed to settle, and a timeout reports missing merge context rather than an index-busy error.
2. Resolve affected `library/*.md`, `records/<id>/metadata.json`, `source.md` and `timeline.md` by understanding both sides. Preserve provenance and history, immutable facts and irreversible lifecycle changes from both parents. Resolve metadata and fact references; the CLI regenerates fact blocks. Remove conflict markers from content. Final rendered bodies must fit 4000 Unicode characters; split by meaning without truncating knowledge when necessary. Same-path creates with different IDs, renames, deletes and incompatible immutable fact histories require manual document-level recovery.
3. Stage the reviewed **content** through `git add` or the editor's resolve/stage action. `record.json` may remain conflicted; do not hand-calculate its hashes. The hook captures unresolved stages plus resolve-undo entries matched to both parents, saving `.docnexus/.runtime/git-merge.json`. Earlier captures survive staging. When content conflicts remain, it waits for another index update.
4. After all knowledge content conflicts have been staged, automatic repair reads the staged versions, validates global knowledge and both parents' fact history, then reconstructs records, hashes, timestamps and fact views and appends a merge event. It keeps the staged source and merged timeline. Navigation refreshes, and only repaired/dependent views and generated navigation are staged. Unrelated index entries are retained. Repeated notifications do not duplicate an unchanged adoption event.
5. Wait for the ready message, then review the staged diff and commit or use `git merge --continue`. A busy index queues a short-lived worker; its timestamped start, outcome and failure lines are in `.docnexus/.runtime/git-merge.log`. When that file reaches 64 KiB it rotates once to `git-merge.log.1`, replacing the previous backup. No project lock is held while waiting on the index. Pre-commit skips code-only commits. For ordinary knowledge edits it hashes only affected document units; fact/entity/relationship changes or document additions/deletions retain global semantic/reference checks without hashing historical source/timeline assets. Unadopted prose reports text_integrity_error and the document sync action. Repaired merges reuse their parent-bound staged Git-object checkpoint and block changed or pending repairs without rereading all document bodies. It does not semantically merge content or create a Git commit.

Automatic writes refuse unstaged knowledge edits, untracked records/navigation and symlinks that could be overwritten. Resolve/stage or preserve those edits, then stage reviewed content again to retry. Errors identify the failing file or invariant. Native hooks cannot be guaranteed for clients that bypass hooks or discard Git index history; local snapshots are not a permanent audit log. If record conflicts remain, Git may reject commit before pre-commit: finish the content staging and wait for index-hook repair first. A failed/crashed index publication can leave repaired working files unstaged; review and stage the document unit again to retry. Preserve pending text journals and inspect interrupted writes instead of deleting or blindly replaying them over merged files. Retrieval indexes update on the next recall or explicit `index sync`.

Install the hooks before resolving and staging merge contents, or explicitly integrate the documented hook commands into the project hook manager. Clean pulls need no adoption. No command pulls, commits or pushes automatically.
